# Content Structure Reference

Read this file before generating vault concept files or Anki deck cards.

---

## Overview

The project has two parallel content systems that must stay in sync:

| System | Location | Purpose |
|--------|----------|---------|
| **Vault** | `content/vault/` | Obsidian-compatible concept reference files (Markdown) |
| **Deck** | `content/decks/interview-prep/` | Anki cards built from the vault concepts |

The bridge between them is the `source_nodes` field on every card — a list of vault concept slugs.

---

## 1. Vault — Concept Files

### Directory layout

```
content/vault/
  adaptation/          ← LoRA, instruction tuning, prompt engineering
  architectures/       ← CNN blocks, ViT, UNet, FPN, attention, flash-attention
  data/                ← active learning, augmentation, test-time strategies
  generative/          ← VAE, GAN, diffusion, normalizing flows, autoregressive
  math/                ← Lagrangian optimisation
  probability/         ← Bayes, sampling, hypothesis testing
  self-supervised/     ← BERT MLM, contrastive learning, knowledge distillation, CLIP, BLIP
  theory/              ← domain adaptation, generalisation bounds
  training/            ← mixed precision, data augmentation, LR schedules
  index.json           ← machine-readable index (auto-generated by build_vault_index.py)
  card_index.json      ← concept coverage index (auto-generated by build_card_index.py)
```

### Frontmatter

Every `.md` file must open with YAML frontmatter:

```yaml
---
title: "Human-readable title"
tags: [kebab-case-slug, another-slug]
aliases: [Alternative Name, another alias]
difficulty: 2
status: complete
depends_on: [prerequisite-slug, another-prereq]
related: [associated-concept, another-concept]
---
```

Field rules:

| Field | Rule |
|-------|------|
| `title` | Full concept name, human-readable |
| `tags` | 3–6 specific topic tags in kebab-case. Concept-level only (e.g. `bayesian-inference`, `mle`). **Never**: organisational tags (`lecture-1`, `chapter-3`), umbrella tags (`machine-learning`, `deep-learning`, `statistics`), or card-type tags (`definition`, `proof`). |
| `aliases` | Common alternate names or abbreviations |
| `difficulty` | `1` = must-read foundation · `2` = important · `3` = enrichment/advanced |
| `status` | `draft` · `in-progress` · `complete` |
| `depends_on` | Prerequisite concept slugs — what must be understood first. Kebab-case filename (no `.md`, no directory). Empty list `[]` if no prerequisites. |
| `related` | Associatively related slugs — connected ideas, not prerequisites. |

General formatting rules:
- Filename is the concept slug (`knowledge-distillation.md` → slug `knowledge-distillation`)
- Use `## ` (H2) for major sections — these appear in `index.json`
- Use `### ` (H3) for subsections
- One concept per file. If content covers multiple concepts, split into separate files.

### Content Rules

#### The primary test

> **A reader should finish the note able to explain the concept in their own words, not merely reproduce formulas.**

Before marking any file complete, ask: *if someone read only this file, could they explain the concept at a whiteboard without looking at formulas?* If the answer is no — even if all other rules below are satisfied — the file is not done. Every other rule is in service of this one goal.

---

#### 1. Order of presentation

Introduce material in this sequence whenever possible:

```
Motivation → Intuition → Simple Example → Formal Definition → Formula → Interpretation → Consequences → Applications
```

Never present a formula before the reader understands why it is needed. Never define a mathematical object before motivating it.

**Bad:**
```
The Fourier Transform is

$$F(\omega) = \int_{-\infty}^{\infty} f(t)\, e^{-2\pi i \omega t}\, dt$$
```

**Good:**
```
Suppose we want to know which frequencies exist inside a signal.
The Fourier Transform answers this question.

Mathematically:

$$F(\omega) = \int_{-\infty}^{\infty} f(t)\, e^{-2\pi i \omega t}\, dt$$
```

---

#### 2. The six questions

Every concept file must answer these questions, in order:

1. What problem does this concept solve?
2. Why was it invented?
3. What intuition should the reader build?
4. What is the formal mathematical definition?
5. How should the formula be interpreted?
6. What practical consequences follow from it?

---

#### 3. Formula discipline

- Define every variable in every formula — no implicit "standard notation."
- After stating a formula, explain what it is *doing*, not just what it *is*.
- When introducing a theorem or formula, provide:
  - the intuition
  - the geometric interpretation (if applicable)
  - the physical interpretation (if applicable)
  - the computational interpretation (if applicable)

---

#### 4. Multi-level explanations

For important concepts, explain from multiple viewpoints when relevant:

- Intuitive viewpoint
- Mathematical viewpoint
- Geometric viewpoint
- Physical viewpoint
- Computational viewpoint
- Machine learning / engineering viewpoint

Different readers build understanding through different lenses.

---

#### 5. Wikilinks

- Use `[[slug]]` syntax to link to related concepts *within the body text*, not only in frontmatter.
- At minimum, wikilink everything listed in `depends_on` and `related` where they naturally appear in the prose.
- Add a `## Links` section at the bottom listing every wikilinked file with a one-line description of the relationship:

```markdown
## Links

- [[knowledge-distillation]] — label smoothing produces soft targets similar to a teacher's logits, but from a uniform prior rather than learned knowledge
- [[loss-cross-entropy]] — label smoothing modifies the target distribution fed into cross-entropy loss
```

---

#### 6. What to avoid

- Do not invent facts. If the source material is incomplete, mark gaps with `[TODO]` rather than filling them with plausible-sounding content.
- Do not add a bibliography or references section unless the original has one.
- Do not add emoji or decorative elements.
- Keep content faithful to the source material — restructure and clarify, do not rewrite the subject matter.

### `content/vault/index.json` — the vault index

Auto-generated by `python3 tools/build_vault_index.py`. Structure:

```json
{
  "adaptation/instruction-tuning.md": {
    "title": "Instruction Tuning and Supervised Fine-Tuning (SFT)",
    "tags": ["instruction-tuning", "sft", ...],
    "aliases": ["instruction tuning", "SFT", ...],
    "sections": [
      {"header": "1. The Gap Between Pretraining and Usefulness", "level": 2, "line": 17},
      {"header": "2. FLAN — Multi-Task Instruction Tuning", "level": 2, "line": 31},
      ...
    ]
  }
}
```

Key: `"folder/filename.md"`. The concept slug is always the filename without `.md`.

Run after adding or modifying vault files:
```bash
python3 tools/build_vault_index.py
```

```
  graph-neural-networks.json
```

### Section file format

```json
{
  "name": "Math Foundations",
  "cards": [
    {
      "card_type": "reveal",
      "question": "[Level] Interview-style question",
      "answer": "2-4 sentence strong-candidate answer",
      "steps": "Deeper follow-up: derivations, edge cases, connections",
      "hint": "Only for non-obvious first moves in proofs/derivations",
      "tags": ["topic-slug", "role:mle", "domain:math", "style:derivation"],
      "source_nodes": ["concept-slug-1", "concept-slug-2"],
      "id": "cfa06291b0351a69",
      "level": "fundamental"
    }
  ]
}
```

Card field rules:
- `card_type` — always `"reveal"` for this deck
- `question` — phrased as a real interview question; prefix `[Paper]` for paper exercise cards
- `answer` — what a strong candidate says in 2–4 sentences
- `steps` — deeper follow-up, derivations, edge cases; supports LaTeX (`$$...$$`)
- `hint` — only include when first move is non-obvious
- `tags` — kebab-case content tags + namespaced metadata tags (see section 2.5)
- `source_nodes` — **required on every card**; list of vault slugs (filename without `.md`, no directory prefix)
- `id` — stable 16-char hex; auto-assigned by generator — do not invent IDs
- `level` — `"fundamental"`, `"intermediate"`, or `"advanced"`

### `content/vault/card_index.json` — the card index

Auto-generated by `python3 tools/build_card_index.py`. Two views:

**`by_concept`** — for each vault slug: which sections cover it, card count, hands-on flag:
```json
"knowledge-distillation": {
  "sections": ["Fine-Tuning & Model Compression"],
  "card_count": 6,
  "has_hands_on": true,
  "missing_types": []
}
```

**`by_section`** — for each deck section: covered concepts, uncovered vault concepts:
```json
"Fine-Tuning & Model Compression": {
  "covered_concepts": ["knowledge-distillation", "lora-quantization"],
  "uncovered_vault_concepts": ["transfer-learning", "rlhf"]
}
```

A concept is "hands-on" if any card has tags in `{derivation, application, proof, algebraic-derivation, paper}` or question starts with `[Paper]`.

Run after adding or modifying cards:
```bash
python3 tools/build_card_index.py
```

## 2.5 Namespaced Tag Convention

Any tag containing `:` is structured metadata. Plain tags (no colon) are
content/concept tags. Both coexist in the `tags` array.

New values can be added under any prefix at any time — no schema migration needed.

**`role:` — who benefits from this card (pick 1–3)**

| Tag | Who |
|-----|-----|
| `role:mle` | ML engineer — training, deployment, optimization |
| `role:ds` | Data scientist — statistics, EDA, modeling |
| `role:cv-engineer` | Computer vision engineer |
| `role:nlp-engineer` | NLP / LLM engineer |
| `role:research` | Research scientist — theory, novel methods |
| `role:eo-specialist` | Earth observation / remote sensing specialist |

**`domain:` — coarse topic bucket (pick 1–3)**

| Tag | Covers |
|-----|--------|
| `domain:ml-core` | Training, optimization, regularization, loss functions |
| `domain:deep-learning` | NN architectures, backprop, initialization |
| `domain:computer-vision` | CNNs, image processing, detection, segmentation |
| `domain:transformers-nlp` | Attention, transformers, fine-tuning, language models |
| `domain:self-supervised` | Contrastive learning, SSL, representation learning |
| `domain:generative-models` | GANs, VAEs, diffusion models |
| `domain:statistics` | Probability, distributions, hypothesis testing |
| `domain:math` | Linear algebra, calculus, optimization theory |
| `domain:earth-observation` | Remote sensing, satellite imagery, spectral analysis |
| `domain:biodiversity-ml` | Species distribution, ecological AI |
| `domain:vision-language` | VLMs, CLIP, multimodal models |
| `domain:production-ml` | Deployment, quantization, distillation, MLOps |

**`style:` — question type (pick 1–2)**

| Tag | Meaning |
|-----|---------|
| `style:conceptual` | Explain what X is and why it works |
| `style:derivation` | Prove or derive the math behind X |
| `style:problem-solving` | Given a setup, compute or solve it |
| `style:practical` | How would you implement / choose / engineer X? |
| `style:tradeoffs` | Compare X vs Y — design or architectural judgment |
| `style:debugging` | What's wrong with this approach / how would you fix it? |

**Tag cleanup rule:** The following tags are redundant with the `level` field and
must not appear on cards: `junior`, `mid-level`, `senior`, `level:fundamental`,
`level:intermediate`, `level:advanced`. Remove them during any card edit.

**Progress tracker:**
```bash
python3 tools/migrate_tags.py   # reports missing namespaced tags + redundant tags per file
```

## 2.6 Card Type JSON — Field Options

Each entry in the `fields` array of a card type JSON supports these options.
The generator reads them at build time — no code change needed to use them.

### Required on every field

| Key | Type | Description |
|-----|------|-------------|
| `name` | string | Key used in card JSON (`"prompt"`, `"answer"`, …) |
| `role` | string | See role table below |
| `required` | bool | Whether a card must supply a value for this field |

### Roles

| Role | Maps to | Notes |
|------|---------|-------|
| `question` | Definition slot (front) | Shown on card front |
| `answer` | Learnable slot | The correct answer; first alternative used for TTS |
| `extra` | Extra 1, Extra 2, … | Shown on card back; multiple extras in order |
| `audio_override` | Injects `[sound:file]` | Pre-generated MP3 filename stored in `media/` |
| `image` | Prepended to question | `<img src="...">` |
| `choices` | Choices slot | `\|`-delimited distractors; auto-filled if empty |
| `cloze` | Text slot | `{{word}}` → Anki `{{c1::word}}` |

### Direction (RTL / LTR)

```json
{ "name": "prompt", "role": "question", "direction": "rtl" }
```

| Value | Effect |
|-------|--------|
| `"rtl"` | Wraps rendered value in `<bdi dir="rtl" style="display:block;text-align:right;">` |
| `"ltr"` | Wraps rendered value in `<bdi dir="ltr" style="display:block;text-align:left;">` |
| *(absent)* | No wrapping — browser default direction |

Use `"rtl"` for Arabic, Persian, Hebrew, Urdu field values.
Use `"ltr"` only when you need to force left-to-right inside a document that is otherwise RTL.

For **inline** RTL text within a mixed field (e.g., a Persian word in an English details string),
wrap the RTL portion manually in the card JSON:

```
🇮🇷  <bdi dir="rtl">متن فارسی</bdi>
```

`<bdi>` (Bi-Directional Isolation) prevents the flag emoji and surrounding LTR text from
inheriting the Persian direction.

### Audio options

| Key | Default | Effect |
|-----|---------|--------|
| `"audio": true` | `false` | Generate TTS for this field; audio file attached to card |
| `"tts_language": "fa"` | card type's `tts.language` | Override TTS language for this specific field |

`audio` on an `audio_override` field is ignored — pre-generated files are used as-is.

### `autoplay` (audio_override fields only)

| Value | Effect |
|-------|--------|
| `true` *(default)* | `[sound:file]` injected into the question slot — plays on card front |
| `false` | `[sound:file]` injected into the answer slot — plays on back reveal |

### Other options

| Key | Default | Effect |
|-----|---------|--------|
| `"latex": true` | `false` | Convert `$...$` and `$$...$$` to Anki MathJax delimiters |
| `"alternatives": true` | `false` | Accept ` ; `-separated synonyms in the `answer` field |
| `"label"` | field `name` | Human-readable column header shown in Anki Browse |

### Example — bilingual card type with RTL prompt and back-reveal audio

```json
{
  "fields": [
    {
      "name": "prompt",
      "label": "Persian Prompt",
      "role": "question",
      "required": true,
      "direction": "rtl"
    },
    {
      "name": "answer",
      "label": "English Word",
      "role": "answer",
      "required": true,
      "alternatives": true
    },
    {
      "name": "audio",
      "label": "Word Audio File",
      "role": "audio_override",
      "required": false,
      "autoplay": false
    },
    {
      "name": "details",
      "label": "Word Details",
      "role": "extra",
      "required": false
    }
  ]
}
```

## 3. The `source_nodes` Bridge

Every card must have `source_nodes`. This is the single link between the two systems.

- Each value is a vault concept slug — the `.md` filename without extension and without directory
- Example: `content/vault/self-supervised/knowledge-distillation.md` → slug `"knowledge-distillation"`
- Cross-topic cards should list all relevant concepts

`source_nodes` drives:
- `content/vault/card_index.json` — which concepts have coverage (built by `tools/build_card_index.py`)
- `vault_footer` injection at build time — "Further reading" links on card backs
- `tools/coverage.py` — gap analysis

---

## 4. Full Post-Change Pipeline

After adding vault files:
```bash
python3 tools/vault_validator.py        # check frontmatter, tags, links
python3 tools/build_vault_index.py      # regenerate content/vault/index.json
```

After adding or modifying cards:
```bash
python3 tools/build_card_index.py       # regenerate content/vault/card_index.json
docker compose up                       # rebuild and serve the deck
```

---

## 5. Coverage Gaps

To find which vault concepts lack cards or hands-on coverage:
```bash
python3 tools/coverage.py               # table view (default)
python3 tools/coverage.py --mode analyze --top 20   # priority ranking
```

Output columns: concept, folder, card count, has hands-on, §vault (H2 section count), missing card types. Sorted by gap score descending.
